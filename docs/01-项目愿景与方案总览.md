## 1. 定位与价值假设

**SpecMill 是面向个人开发者的本机开发续做工作台，通过轻量 Web 与薄 CLI，把规格、进度、证据和下一步连接起来，让开发者在中断或切换工具后继续推进同一项变更。**

它的长期方向是通用开发流程工作台；首版先解决一个具体问题：我在工具 A 中做到一半，换到工具 B 或开启新会话后，如何知道依据是什么、实际做到哪里、哪些结论可信、接下来该做什么。

首版不要求换掉已有编辑器、编码 agent、测试工具或 Git 流程。工作台保存明确的开发记录，生成可阅读的交接材料；实际开发与测试继续在外部工具中完成。用户保留范围变更、风险接受和最终验收的决定权。

这个方向有价值的前提，是它减少重新解释和查证上下文的成本，而且保存记录的负担小于节省的时间。目前这是待验证的产品假设，不能仅凭完整的设计文档认定成立。如果普通 Markdown 交接已经足够，而结构化记录持续增加负担，就应缩减功能，而不是继续增加流程。

## 2. 首版的使用者与核心问题

首位使用者是项目作者本人：一个人在同一台开发机上，使用多个开发会话或工具，持续推进自己的项目。

| 真实问题 | 首版提供的能力 | 需要守住的边界 |
|---|---|---|
| 新会话不知道原来的目标与取舍 | 冻结规格基线，区分已批准决定和待确认建议 | 摘要不能擅自扩大范围 |
| 中断时还有未提交、未通过测试的修改 | 在关键节点保存进度、工作区观察和下一步 | 保存进度不等于备份源码 |
| 换工具后重复调查或覆盖旧工作 | 生成 Markdown 交接，续做时核对实际文件，显式切换写会话 | 工作台不能锁住外部工具的源码编辑 |
| “测试通过”无法对应具体要求或版本 | 条件、实现目标、证据和验收决定关联 | agent 建议不等于用户批准 |
| 逐条点确认成本太高 | 集中审阅后批量确认明确选中的合格条件 | 缺证据、失败和豁免不能被一键掩盖 |
| 担心数据绑定在工作台中 | 导出并恢复记录和受管理附件 | 源码和开发环境需另外准备 |

其他人可以帮助检验交接材料是否看得懂，但首版不建立多人账号、责任分配、审批链或责任接管流程。

## 3. 已确认的首版边界

以下是用户在 Q1—Q13 中确认的产品决定。它们约束实现；具体存储和接口形态见详细设计，属于落实这些约束的工程方案。

| 问题 | 已确认决定 |
|---|---|
| Q1 | 个人跨会话、跨工具续做优先；多人责任交接后置 |
| Q2 | 按冻结的规格与实现版本验收；不强制追随上游最新版本 |
| Q3 | 数据可导出、可恢复；不要求每次操作都写 Git |
| Q4 | 本机 Web＋本机薄 CLI；首版不提供远程托管和实时多机同步 |
| Q5 | 代码未提交、测试未通过时仍可保存进度；正式验收另有证据要求 |
| Q6 | 通过显式 Markdown 交接和薄 CLI 写回；不自动收集全部聊天 |
| Q7 | agent 记录和提议；用户确认关键决定 |
| Q8 | 恢复范围是工作台记录与受管理附件；不承诺恢复全部开发现场 |
| Q9 | 同一变更只有一个活跃写会话；不同变更并行时使用不同工作区 |
| Q10 | 在关键节点保存进度，允许手动补存；中断只保证最后成功保存点 |
| Q11 | Web／CLI 是工作台记录的统一写入口；交接 Markdown 仅为输出 |
| Q12 | 支持明确选项的批量验收、证据复用确认；保留每项独立决定 |
| Q13 | 普通 Markdown 和显式选择先落地；Spec Kit 自动导入后置 |

原生规格 Markdown 仍可在编辑器中修改并按正常 Git 流程管理。Q11 限制的是**生成的交接材料**，不把项目内所有 Markdown 变成只读文件。

## 4. 一个完整的首版闭环

1. **建立变更。** 用户登记已有项目工作目录，选择普通 Markdown 中的规格依据，写清目标、范围、不做事项和验收条件，确认规格基线。
2. **开始开发。** 工具 A 获取该变更的写会话，读取已确认依据，在真实工作目录中开发。工作台不负责启动 agent 或运行测试。
3. **保存进度。** 在关键测试、暂停或切换工具前，保存已做事项、失败与缺口、工作区状态和下一步。即使代码未提交，也可形成续做保存点。
4. **显式交接。** 生成带版本与时间的 Markdown。正常切换释放旧写会话；意外中断则由用户显式接管，旧会话失去后续写回能力。
5. **核对并续做。** 工具 B 读取材料和工作台最新记录，检查实际文件与保存点的差异，说明差异后继续。它不能把交接摘要当成当前源码的替代品。
6. **提交证据。** 开发与验证完成后，关联可核对的实现版本、验收条件和测试依据。未提交阶段的记录保留为过程信息，不自动升级为正式通过证据。
7. **用户验收。** 用户审阅当前冻结版本和证据，对明确选中的条件批量确认；风险豁免单独决定。满足条件后标记该版本已验收。
8. **导出与恢复。** 导出项目恢复包，在独立的数据目录中恢复记录与附件；另行准备源码，重新绑定工作目录并核对，才能继续开发。

“已验收”只回答某个冻结版本是否满足本次条件，不意味着已合并、已上线，或远端分支没有更新。

## 5. 首版功能范围

### 5.1 页面

Web 保持两级入口：项目列表与项目页；从项目页进入变更详情。变更详情只有四个工作区：

| 工作区 | 用户主要动作 |
|---|---|
| 续做 | 读取当前上下文、保存进度、查看实际工作区差异、切换写会话、生成交接材料 |
| 规格 | 选择普通 Markdown 依据，维护草案，确认或更换冻结基线 |
| 验收 | 核对实现目标、证据、失败与缺口，批量确认、单独豁免、最终验收 |
| 历史与导出 | 查看保存点、会话切换、历次决定和固定交接快照，导出恢复包 |

不单独建设组织后台、任务调度台、聊天窗口或通用仪表盘。项目页负责工作目录绑定和项目恢复入口。

### 5.2 必须具备的能力

- 从普通 Markdown 显式选取依据与条件，保留可核对的冻结内容。
- 将持续变化的开发进度与固定的规格基线、验收版本分开。
- 单个变更只接受一个活跃写会话的进度、证据和建议；拒绝过期写回。
- Web 与薄 CLI 使用同一套数据和规则，生成固定快照对应的交接 Markdown。
- 将证据关联到具体条件和实现版本；由用户批量确认或明确接受风险。
- 可靠地保存、导出和恢复记录与受管理附件，清楚展示保存失败、缺失文件和版本不一致。

### 5.3 首版不做

- 多人责任交接、账号组织、细粒度角色和远程服务部署。
- 自动运行 agent、自动修改源码、收集所有会话、代替用户批准关键决定。
- 源码备份、工作区回滚、依赖环境恢复、远程仓库镜像及实时多机同步。
- 每个操作自动提交 Git、专用记录分支、Git 与数据库双写事务。
- Spec Kit 专用解析器、通用插件平台、双向 Markdown 编辑同步。
- 自动合并、发布、CI 调度以及“所有开发工具均已兼容”的承诺。

这些不是隐藏的首版依赖。后续是否增加，要由真实使用问题推动。

## 6. 数据与系统边界

工程默认方案采用**单个本地服务＋SQLite 工作台记录＋受管理附件目录**。轻量 Web 与薄 CLI 都通过本地服务访问相同业务规则；CLI 不直接改数据库。语言、框架和打包工具的推荐方案见[技术选型](03-首版技术选型.md)，不改变本文的产品边界。

| 数据 | 权威来源 | 工作台的职责 |
|---|---|---|
| 源码、原生规格文件 | 用户项目工作目录和正常 Git 流程 | 只读观察、记录引用；保存选定规格的冻结内容 |
| 变更、进度、基线、证据关联、用户决定 | 本地工作台数据库 | 统一校验写入、保留历史、导出和恢复 |
| 上传并纳入管理的日志、截图等附件 | 工作台附件目录 | 保存内容、校验完整性、纳入恢复包 |
| 交接 Markdown | 固定交接快照的生成结果 | 提供可读上下文；修改文件不回写记录 |
| 外部 URL 和本地外链文件 | 原位置 | 只保存引用；除非显式复制为附件，否则不保证恢复其内容 |

工作台记录可导出不等于全部数据公开。恢复包可能包含用户主动纳入的规格摘录、日志和截图；导出前显示内容范围。公开仓库仅发布产品代码、文档和脱敏示例，不自动发布个人工作台数据。

本机服务默认仅监听回环地址，区分读取、agent 写回和用户确认入口，不把 localhost 当作天然免鉴权环境。同一操作系统用户拥有文件和进程控制权时，首版不宣称能隔离恶意 agent。

## 7. 判断首版是否成立

先完成一次真实的小变更，再评估是否值得扩大范围。样本必须包含中途未提交修改与一次实际会话或工具切换，不能用空项目上的全程顺畅演示代替。

| 维度 | 验证方式 |
|---|---|
| 能接着做 | 工具 B 能说明目标、当前状态、缺口和下一步，并核对实际文件后继续 |
| 没有制造假上下文 | 旧写会话、过时交接、未确认建议和未提交证据不会变成当前有效结论 |
| 能完成验收 | 冻结版本条件与证据一一对应，用户能批量确认，豁免可见 |
| 数据可带走 | 导出后在独立数据目录恢复全部记录与受管理附件；缺失源码被明确提示 |
| 使用负担合理 | 记录保存和确认耗时可记录、可比较；不要求重复粘贴完整聊天或维护两套文档 |

记录一次不用工作台的交接成本，再与试用过程比较；样本不足时只记录观察，不给出夸大的效率提升百分比。两种实际工具的成功样本只能证明这两种组合，不代表所有工具已验证。

## 8. 迭代路线

### 阶段一：v0.1，验证个人续做闭环

实现本文限定的页面、保存点、单写会话、Markdown 交接、冻结版本验收和恢复包。验收对象是完整的小变更闭环与失败场景，不是孤立功能数量。

### 阶段二：降低日常使用成本

根据真实样本优化摘要长度、证据关联、批量审阅、错误恢复和安装体验；补充实际使用的第二种工具接入说明。如果记录步骤长期比恢复上下文更费时，优先简化记录格式。

### 阶段三：按需接入现有规格与开发工具

出现稳定、重复的导入成本后，再增加 Spec Kit 等专用导入和工具辅助接入。适配器只负责读取与映射，不能改变核心验收语义。暂不为所有可能工具预设插件接口。

### 阶段四：重新评估多人及多机需求

只有个人续做机制被证明有用，且存在明确协作场景时，才设计责任交接、账号权限、远程部署或同步冲突。它们是新范围，需要单独设计与验收。

## 9. 开源交付方向

目标是后续同步到 GitHub，公开迭代。首个可运行版本应提供安装启动说明、真实但脱敏的续做示例、能力边界、数据位置以及导出恢复说明。

在实际发布前选择开源许可证、确认仓库与发布方式，排除凭据、个人记录和真实项目附件。当前只完成设计文档，不因“未来开源”自动执行建库、提交、推送或发布。

## 10. 当前设计的限制与下一步

剩余不确定性主要是实际使用效果和工程实现成本：摘要是否足够、保存操作是否打断开发、两个实际工具能否按协议协作、附件规模是否影响恢复。详细设计给出可实施的默认规则与验证场景，但不把它们表述为已运行事实。

当前已补充[技术选型](03-首版技术选型.md)与[最小闭环实施计划](superpowers/plans/2026-11-14-v0.1-minimum-loop.md)，进入编码时按计划逐步验收。当前不追加代码，不再沿用旧方案中的多人责任门禁、强制远端刷新、专用记录分支和首版 Spec Kit 自动导入要求。
