## 1. 系统边界与不变量

首版只有一个人类使用者。开发工具是外部执行者，不是工作台内置 agent；会话是该开发者的一次工具使用，不是多人身份或责任关系。

1. 同一变更最多一个活跃写会话。读取不限于该会话；工作台无法禁止外部进程直接改源码。
2. 进度可在未提交、测试失败时保存。保存成功、代码已备份、验收通过是三个不同事实。
3. 规格基线、实现目标、证据和决定均可追溯到固定版本；改变当前版本不覆盖历史。
4. agent 可以记进度、提交证据与建议；采用范围变更、接受豁免和最终验收由用户确认。
5. Web／CLI 共用工作台记录与业务规则；生成的交接 Markdown 不接受编辑回写。
6. 批量确认仍保存每项独立决定，不能把未知、缺失或失败的项目隐式视为通过。
7. 工作台恢复只覆盖记录与受管理附件。没有另行备份的源码修改不能从保存点找回。
8. “已验收”绑定冻结版本；不以联网、刷新远端、合并或发布为完成前提。
9. GitHub Issues 是本仓库的待办与讨论入口，仓库文档保存设计；工作台独立保存冻结依据、续做与验收记录。首版只保留必要链接，不同步状态，也不把关闭 Issue 当作验收。
10. 项目累计写入受完整导出恢复的容量预算约束；接近上限提示，突破预算的新增写入拒绝，已有记录仍可读取与导出，不自动删除历史。
11. 变更之间独立冻结与验收；首版不做跨变更冲突检测或维护全项目唯一最新规格，各变更通过不代表其合并结果已经验证。

## 2. 页面与操作入口

### 2.1 项目列表与项目页

项目列表显示项目名称、已绑定工作目录、进行中的变更数量，以及数据恢复或目录缺失提示。空状态提供“登记现有项目”和“从恢复包恢复”；不自动创建、克隆或扫描用户所有仓库。

项目页提供变更列表、新建变更、工作目录绑定、恢复状态及项目恢复包导出。首版一个项目关联一个 Git 仓库，可登记多个属于该仓库的 worktree 作为工作区；多个仓库作为不同项目登记。

项目页显示容量用量、预算和预警；保存或上传超出累计预算时，Web／CLI 明确返回容量拒绝，保留待提交内容并说明工作台未保存。触顶不隐藏历史或禁用已有数据的导出入口；需经验证支持更高额度后再继续新增。

绑定时核对实际目录、Git 仓库标识和当前 HEAD，展示分支及未提交修改。路径只是本机位置，不是稳定项目身份。移动目录或迁移机器后须重新绑定。无效目录不影响读取历史记录，但禁止依赖该目录的新观察与验收。

项目身份使用工作台生成的 ID。本机判断 worktree 是否属于同一仓库时核对规范化 Git common directory；远端 URL 仅作提示，不把 URL 或路径当作跨机器的唯一仓库身份。恢复后由用户明确选择对应仓库，并校验所引用的提交是否存在；不能仅凭目录同名自动绑定。已初始化但尚无提交的仓库可保存草案和进度，HEAD 标记为空；正式代码验收须等到具备可核对提交。

工作区绑定是当前本机配置，不改写历史。更换已有绑定前须正常结束占用它的写会话，或由用户接管并关闭；只接管但仍保持会话活跃时仍禁止更换。重绑定由用户明确操作，重新核对目录、仓库与文件，再开始新会话。历史保存点与观察保留当时的路径和仓库信息，不通过当前绑定反向改写。开始会话与重绑定必须在事务内校验占用及绑定版本，拒绝两者并发造成的错误关联。

### 2.2 变更详情：四个工作区

页面顶部固定显示目标、业务阶段、规格基线、候选或已确认实现目标、活跃写会话、最后成功保存时间。状态说明必须区分“记录已保存”“存在未提交修改”“尚未验收”。

| 工作区 | 内容与主要操作 | 重要状态 |
|---|---|---|
| 续做 | 当前依据、最近保存点、已做／未做／失败、下一步、工作区对比；保存、开始／结束会话、显式接管、生成交接 | 未保存、保存失败、快照过时、旧会话失效、工作区缺失或差异未核对 |
| 规格 | 普通 Markdown 选择与预览、规格条目、范围与非目标、验收条件；保存草案、对比并采用新基线 | 无依据、依据文件已变但未采用、待用户确认的范围建议 |
| 验收 | 当前审阅版本、逐项证据与结论、未解决失败、候选复用、选中项预览；批量确认、单独豁免、最终验收 | 无实现目标、证据不足、版本不符、确认预览已过期、含豁免 |
| 历史与导出 | 保存点、执行记录、基线与目标变更、会话切换、逐项决定、交接快照；查看旧版本、生成交接、导出恢复包 | 历史不适用于当前版本、外链不可用、附件缺失、导出失败 |

正常空状态应给出下一步，如“尚无保存点，可先记录当前进度”。读取失败保留当前界面并给重试入口；写入失败不得显示成功，不清空用户尚未提交的表单。验收列表支持键盘选择，并在确认前展示准确的选中数量、版本、排除项与原因。

### 2.3 用户与工具的权限边界

- 用户在本机 Web 中确认基线、验收目标、复用、豁免、最终验收、异常接管和重新打开变更。
- 薄 CLI 负责读取、会话操作、保存进度、记录外部执行与证据、提交建议、生成交接。正常开始或释放自己的写会话无需逐步请求用户批准。
- agent 凭据不包含用户确认权限。服务端按凭据能力决定权限，不能因为请求里写了“用户”就接受关键决定。
- 本地服务默认仅监听回环地址；校验请求来源，提供本机启动时的用户访问凭据与独立 CLI 凭据。浏览器写操作防跨站请求，凭据不写入交接或恢复包。
- 这用于阻止误操作和普通越权请求，不是同一 OS 用户下对恶意 agent 的强隔离。能读取整个数据目录和控制进程的工具不在此隔离保证内。

## 3. 核心数据模型

### 3.1 实体与关系

下列是逻辑模型，不要求一项对应一张表。一般可变记录携带版本号；基线、保存点、证据内容和决定一经保存，修改以新增版本或新记录表达。

| 实体 | 关键内容 | 关系与规则 |
|---|---|---|
| Project | ID、名称、仓库标识、本机绑定配置 | 一个仓库；包含变更与工作区 |
| Workspace | ID、项目、规范化路径、仓库身份、绑定版本、最近观察 | 多个 worktree 可属同项目；路径需本机验证；活跃会话禁止更换绑定 |
| SpecItem／Revision | 稳定条目 ID、修订 ID、文本、来源快照引用 | 同一行为修订不复用旧修订号；不依赖标题或行号作为身份 |
| SourceSnapshot | 选定 Markdown 原文或摘录、相对路径、内容摘要、采集时间、可选 commit | 只保留明确选定的依据；属于记录，不可作为第二份可编辑规格 |
| Change | ID、标题、草案、当前基线／目标、阶段、周期、记录版本 | 不引入多人负责人模型；说明性备注与范围契约分开 |
| Baseline | ID、目标、范围、非目标、规格修订和条件集合、确认人及时间 | 用户冻结；采用新基线只更换当前引用 |
| Criterion／Revision | 稳定 ID、修订 ID、可核对预期、所需证据方式 | 条件语义改变产生新修订；任务清单不自动成为验收条件 |
| ImplementationTarget | ID、仓库身份、完整 commit、确认信息 | 不用可移动分支作为验收版本；一个变更可有历史目标 |
| WriterSession | ID、变更、工具标签、工作区、代次、状态、起止时间 | 同一变更最多一个活跃写会话；代次用于拒绝失效写回 |
| WorkspaceObservation | 观察时的路径／绑定版本、仓库／HEAD／分支、脏状态、变更文件清单与摘要、采集时间及覆盖限制 | 不随重绑定改写，不保存源码内容，不代表源码备份或完整环境指纹 |
| Checkpoint | ID、变更周期／版本、基线、会话、观察、进度正文、缺口与下一步 | 已成功保存的续做保存点；不可原地修改历史 |
| Run | ID、会话、外部工具、命令或方法、时间、结果摘要、环境说明 | 记录外部执行尝试；首版不调度或执行命令 |
| Evidence | ID、Run／附件引用、条件修订、基线、实际验证版本、结果、来源与可信边界 | 上传不等于通过；注明由工具报告还是本地观察 |
| AcceptanceProposal | 目标上下文、建议结果、证据引用、理由 | agent 建议或用户草稿，不是有效验收决定 |
| Decision | ID、条件修订、基线、目标、周期、结果、证据、理由、用户、时间 | 结果为通过／失败／豁免；保留被替代记录与替代关系 |
| FailureDisposition | ID、失败证据引用、当前审阅上下文、处置类型、补测证据、理由、用户与时间 | 类型为已解决／不适用；不可变，修订保留替代关系；豁免仍由 Decision 表达 |
| HandoffSnapshot | ID、捕获的变更版本、保存点、基线、目标、相关证据与决定、生成时间 | 固定交接内容；后续材料由此生成 |
| Attachment | 内容摘要、大小、媒体类型、原文件名、存储引用 | 仅显式纳入管理的内容才保证导出恢复 |

核心关联是“项目 → 变更 → 固定基线／目标 → 条件 → 证据与用户决定”。保存点描述开发过程；交接快照把某一时点需要继续工作的记录固定下来。

### 3.2 规格输入与版本规则

首版读取用户选中的普通 Markdown，不依赖 Spec Kit 目录结构或特殊语法。用户明确选择规格依据，编辑或确认可测试的验收条件。系统可以预填标题与摘录，但不得自行推断所有条件已经成立或已获确认。

原生规格文件仍在项目中正常编辑。工作台保存选定内容及摘要作为冻结依据；未提交规格也可由用户确认成内容确定的基线，界面标注其来源尚未提交。保存冻结文本不是备份整个文档目录。

采用新基线时展示目标、范围、条件的变化和受影响的证据。增加、删除或改变条件必须用户确认。条目和条件通过稳定 ID 对应；无法匹配的内容提示用户确认，不按标题相似度自动继承通过结论。标题、说明备注等非契约信息改变，不单独触发整体验收失效。

项目文件随后变化只产生“来源已变化”的提示，不自动替换基线或阻塞当前冻结版本验收。用户决定采用后，才切换到新基线并重新判断证据适用性。

不同变更可引用同一规格条目的不同修订，各自基线独立。某变更采用新修订不切换另一变更的基线，也不触发跨变更冲突检测；不建立全项目唯一最新规格或自动判断语义冲突。各自验收只证明各自冻结版本满足条件，代码集成由正常 Git 流程和人工审阅处理；原生来源文件变化提示仍按上段规则保留。

### 3.3 保存点的最小内容

一次保存至少包含：当前目标与依据引用、已做事项、已知失败／未验证内容、下一步，以及工作区观察。Draft 尚未冻结基线时，基线引用为空，保存草案的固定修订与“未确认”标记；已有基线时引用该基线。阻塞项和待用户确认的决定显式列出；没有相关内容时填写“无”或“未知”，不以空白冒充已检查。

工作区观察读取 HEAD、分支、Git 状态及变更清单，记录已跟踪差异摘要和选定未跟踪文件的摘要。忽略文件、过大文件或无法读取的内容明确标记未覆盖。采集前后状态发生变化时标记观察不稳定，要求重新核对，不能宣称完整一致。

摘要只能帮助发现差异，不能恢复文件，也不能证明所有依赖与运行环境一致。下一步命令只是建议，不自动执行。原始聊天不自动收集；需要留下的决定与原因由工具或用户明确记录。

### 3.4 证据与验收上下文

首版工程默认要求正式代码验收指向**可在已绑定仓库核对的完整 commit，且验证发生在与该 commit 对应的干净工作区**。不强制推送远端；冻结规格以保存的内容版本为准。无提交或含未记录修改的执行仍可保存为进度和参考证据，但不能自动作为正式通过依据。

证据记录实际验证的版本、方法、预期与观察结果、命令退出状态或人工检查结论，以及必要日志或截图。CLI 采集时的工作区状态与工具报告的测试时状态分别记录，不能用“上传时干净”替代“测试时干净”。首版不提供独立测试执行证明：工具报告必须明确标识，用户依据内容决定是否接受。

有效审阅上下文由“变更周期＋基线 ID＋条件修订 ID＋实现目标 ID”确定。历史证据保留，但以下情况不能自动沿用：

- 规格基线或实现目标改变，需要重新判断相关证据是否适用。
- 当前上下文有相关或适用性未知且尚未处置的失败、证据缺失、附件损坏或版本无法核对。
- 只提供测试计数或口头完成声明，无法对应条件及检查方法。
- 旧证据对的是另一版本；即便代码看似无关，也必须明确复用理由。

证据复用是用户为当前上下文作出的新决定，引用原证据并记录适用理由，不改写原始验证版本。允许集中确认多个已审阅的复用项；复用不是绕过尚未解决的失败。

## 4. 生命周期与并发规则

### 4.1 变更阶段

| 阶段／操作 | 前提与结果 |
|---|---|
| Draft → Working | 用户确认规格基线；可以在 Draft 保存草稿进度，但不能最终验收 |
| Working → Reviewing | 提交验收建议，列出候选实现目标与缺口；用户确认审阅目标后才可生成有效确认预览 |
| Reviewing → Working | 需要继续实现或用户采用新基线；保留旧证据和决定，重新核对适用性 |
| Reviewing → Accepted | 当前上下文每项条件均有有效通过或显式豁免，无仍阻塞该上下文的失败；由用户最终确认 |
| Draft／Working／Reviewing → Canceled | 用户明确取消，保留原因和历史，关闭写会话 |
| Accepted／Canceled → 重新打开 | 用户明确重新打开，周期加一；尚无基线的已取消草稿回到 Draft，其余在用户确认继续采用的基线后回到 Working；历史保持不变，新周期重新核对适用性 |

暂停或结束工具会话不改变业务阶段。已验收不等于已合并或已上线；含豁免时显示“已验收，含 N 项豁免”。重新打开后历史通过不自动成为新周期的当前通过。

更换已确认实现目标需要用户确认并重新生成审阅上下文。Reviewing 期间若决定把新增代码纳入本次验收，应采用新的实现目标，再生成预览；仅有工作目录或上游出现尚未采用的新修改，不自动改变当前冻结目标，也不阻塞对旧目标的验收。已完成周期不再接受 agent 追加或改写；发现后续问题由用户记录并重新打开或建立新变更。

### 4.2 单个活跃写会话

开始会话以原子方式占用变更及工作区；同一规范化工作目录不能同时分配给不同变更的活跃写会话。不同变更可并行，但需使用独立工作区。此约束仅覆盖工作台登记的会话，不是文件系统锁。

正常切换：旧会话成功保存并释放，新会话读取最新版本后开始。若旧工具失联、崩溃或未释放，由用户查看最后保存点后显式接管；接管使代次递增，并撤销旧写凭据。过了多久没有活动只能作为提示，不能自动夺取会话。

每次 agent 写回都携带会话 ID、代次、预期变更版本与相关基线／目标。服务端在写事务中重新校验。旧代次、错误工作区、已结束会话和过时记录版本一律拒绝，不按时间戳覆盖。被拒绝的内容可留作未提交草稿供重新核对，但不能自动重试覆盖新状态。

Web 用户的修改同样递增记录版本；人工操作不会被后到达的旧 CLI 请求覆盖。进入 Accepted／Canceled、异常接管和恢复数据均撤销既有写凭据。取到新的写权限不代表已核对真实文件，续做仍需执行下节流程。

Web 手动保存进度同样归属当前有效写会话；没有活跃会话时可建立手动会话，有活跃工具会话时使用该会话上下文并按记录版本校验，不另开并行写会话。用户确认基线、审阅和备注属于用户管理操作，仍按同一记录版本串行写入。每份记录分别保留实际提交者与所属会话，不能把用户手动填写标成 agent 报告。

### 4.3 批量确认的事务边界

用户先查看固定预览：基线、实现目标、逐项证据、适用性、失败、拟作出的决定和准确的选中集合。默认不选中不合格项；前端禁选之外，服务端再次校验。

预览展示最近一次工作区观察及时间，若实际文件与目标不同，明确提示未采用修改不在本次验收范围。最终确认文字始终指明冻结 commit，而非“当前目录”。预览失效依据是工作台审阅上下文或证据改变，不依赖持续监测外部文件；已有完整依据且目标仍可在本地核对时，单纯文件变化不使旧版本证据失效。接受冻结版本后，尚未纳入的修改需另建变更或重新打开后继续。

确认请求绑定预览时的记录版本、条件集合、证据引用和决定类型。提交前任何相关数据变化，整个批次拒绝并重新预览，不静默只确认其中一部分。成功时为每项写独立 Decision，并返回准确结果；不创建含糊的“全通过”总记录。

缺证据、失败未解释或版本不明的项目不得批量通过。风险豁免走单独明确的用户操作，显示缺口、原因、范围和影响；不能夹带在批量通过中。通过或失败决定被修订时，新增替代记录，不修改旧决定。

对新的失败报告，先依据变更周期、基线、条件修订和实现目标判断适用性。明确发生在其他版本且与当前上下文无关的失败保留并提示，不自动阻塞当前冻结目标；不能仅凭 commit 不同推断它与当前目标无关。相关或适用性未知的失败使对应条件待处理并阻止最终验收，不因后上传成功记录自动解除。

用户可以确认补测已解决某条失败，明确关联失败与补测证据并说明理由；也可以认定失败不适用于当前上下文，记录判断依据。两者保存为 FailureDisposition，可在固定预览中集中审阅确认，采用与批量验收相同的版本校验及全批次事务规则。预览必须列出每条失败、处置类型、上下文、证据与理由；新失败或相关数据变化后重新预览。处置只解除所指明失败在该上下文的阻塞，不自动把条件变为通过，不改写原证据，也不把失败的验收决定自动改为通过；仍须形成有效的当前验收决定。改变上下文后重新判断处置适用性。

接受尚未解决的风险仍走独立豁免，记录具体失败／缺口、原因与影响，不夹带在“已解决／不适用”的批量确认中。原失败、处置和替代关系都保留，不能删除失败来完成验收。

最终验收再校验所有当前条件、失败适用性与有效处置／豁免，固定完成快照，关闭写会话。可提供“确认选中项并完成验收”，但必须在同一事务满足所有条件；事务失败时不得留下半完成状态。

## 5. 完整续做、交接与验收流程

### 5.1 建立变更与首次开发

1. 绑定本机项目与工作区，显示现有未提交改动；不清理、不切换分支。
2. 建立目标与草案，选取 Markdown 依据，用户确认范围、非目标与验收条件。
3. 工具 A 开始写会话，读取基线与已有进度。已有修改的归属不清时，先说明并核对，不覆盖。
4. 工具 A 在外部开发。关键测试、形成可解释的阶段进展、暂停或换工具前保存；用户也可随时要求保存。
5. 写入成功后返回保存点 ID 和记录版本。若失败，明确说明仍未保存，不生成虚假的最新成功点。

### 5.2 生成交接材料

交接快照固定本次所用记录及其版本，从中生成 Markdown，顺序为：

1. 项目、变更、快照 ID、生成时间、当前业务阶段。
2. 目标、范围与非目标、冻结基线、待确认建议。
3. 最近保存点、已做事项、工作区观察及覆盖限制。
4. 已验证、失败、未验证与证据引用，明确其版本及来源。
5. 阻塞项、下一步、建议检查步骤。
6. 续做须知：查询最新记录、核对实际文件、取得有效写会话；记录不包含源码备份。

界面分别标注“保存点已保存”和“交接文件已生成”。生成失败不撤销已成功的保存点，可按同一快照重试。默认输出到工作台管理的导出位置；写到用户指定路径前不覆盖未知现有文件。

直接修改生成的 Markdown 不回写工作台。管理目录中材料与生成摘要不符时提示已被修改，可输出新的副本；外部复制件仍按普通文本对待。新会话必须按快照 ID 查询工作台当前版本，不能因为材料日期较新就认定有效。不能导入交接 Markdown 替代项目恢复包。

### 5.3 中断后或切换工具续做

1. 工具 B 读取交接材料，再查询当前基线、变更版本、最近成功保存点和写会话状态。
2. 核对绑定目录与仓库身份，重新观察 HEAD、分支、未提交修改和相关文件。
3. 若文件状态比保存点更新，列出差异及来源；可能是未保存的新工作，不能自动回退或覆盖。材料比工作台旧时读取新记录；源码缺失时仅能浏览记录，不能声称恢复开发现场。
4. 正常释放后开始新会话；旧会话仍活跃时，由用户显式接管。工具 B 获取权限后提交核对结论作为新的进度记录。
5. 若差异可解释且仍在已批准范围内，继续开发；范围变化作为建议交用户确认。无法解释的并发改动先停止受影响的写操作，保留现场供核对。
6. 完成下一关键节点后保存新进度；只保证最后成功保存点，不能假设未落盘的聊天或操作已被记录。

### 5.4 形成正式证据与完成验收

1. 在外部正常开发流程中形成可核对的提交，不要求工作台代为提交或推送。
2. 在对应干净工作区执行检查，将实际版本、方法与结果保存为证据；首版只记录外部执行，不替代测试工具。
3. 工具提交验收建议。用户核对并确认实现目标；界面展示与当前基线的关联。
4. 对不适用的历史证据重新验证或提出复用理由；对失败与缺口明确处理。无法核对的引用不能成为正式通过依据。
5. 用户选择已审阅的合格条件，批量确认。需要接受风险的条件单独豁免。
6. 全部条件具备有效决定后，用户完成验收。固定完成快照并关闭写会话，保留逐项结果和豁免。
7. 远端更新只作为信息；冻结版本和证据在本地可核对时无需联网。若用户采用更新后的规格或代码版本，按新上下文重新审阅。

## 6. 本地架构与持久化

### 6.1 最小模块边界

| 模块 | 职责 | 不承担的职责 |
|---|---|---|
| 本地应用服务 | 变更、会话、版本校验、证据适用性、用户确认与查询 | 执行 agent、编辑源码、远程同步 |
| 记录与附件存储 | SQLite 事务、不可变附件、历史、导出恢复 | 向 Git 写业务记录、双写协调 |
| 工作区观察 | 读取指定仓库的状态和文件摘要，保留观察时的绑定信息 | 自动 fetch、checkout、reset、commit、push |
| 交接生成 | 固定快照和可阅读 Markdown | 解析编辑后的材料并回写 |
| Web／薄 CLI | 用户操作与工具协议入口 | 绕过服务直接写数据库、各自实现业务规则 |

以上可位于同一进程和代码库，不拆微服务，不引入消息队列或预先建设插件平台。SQLite 和附件位于应用管理的数据目录，独立于项目仓库；本机路径与公开产品源码分离。

### 6.2 写入原子性与失败处理

一次记录变更在单个数据库事务中完成：权限、会话代次和预期版本校验，写业务记录及历史，更新当前引用，保存幂等回执。记录的当前状态与历史不能分两步独立成功。

凡增加项目导出内容的写入，还须原子核对项目累计容量；不同变更并行也不能分别通过预检后合计超限。预算覆盖历史、快照、决定及其元数据，而非只计算当前正文。容量拒绝不前移保存点、不留下半批结果，也不把未保存内容标为成功；幂等重放已完成请求不重复消耗容量。细化计量与导出开销见技术选型 §5。

CLI 写请求使用幂等键。网络超时后先按同一键查询或重试：相同内容返回已有结果，不新增重复保存点或决定；相同键配不同内容拒绝。返回历史回执不等于恢复旧会话的写权限，尚未提交的旧请求仍必须通过当前代次校验。

附件先写入受控临时位置并完成大小、类型和内容摘要校验，再移到内容寻址的不可变位置，最后由数据库事务建立引用。文件写入失败不得生成有效引用；数据库失败可遗留未引用文件，后续仅清理已确认无引用且不在导出中的暂存内容。不能因一次失败清理掉已被历史引用的附件。

交接 Markdown 是事务完成后的派生输出；生成失败单独重试。磁盘满、数据库锁定或服务退出都不得显示“已保存”，客户端保留可重试内容。等待时长和大小限制按[技术选型](03-首版技术选型.md)第 5 节统一配置并纳入错误提示，不留无限等待。

服务启动先检查存储版本与可读性，发现不支持的 schema 或损坏时进入明确的不可写状态。首版不承诺任意未来格式兼容；升级涉及迁移时须提供迁移前备份和失败回退方案。

### 6.3 薄 CLI 的能力面

以下是协议能力，不是已实现的命令语法：

| 能力 | 输入／输出约束 |
|---|---|
| 读取变更与最新上下文 | 返回基线、记录版本、保存点、会话状态和可核对的引用 |
| 开始／释放会话 | 原子占用或释放；返回会话与代次，不能自行强制接管他人活跃会话 |
| 保存进度 | 结构化进度、观察、预期版本；返回保存点 ID |
| 记录执行／证据 | 实际版本、方法、结果、条件关联和附件；声明来源 |
| 提交变更／验收建议 | 只创建待用户确认的建议，不直接改变批准结果 |
| 生成交接 | 指定快照或当前已保存记录；返回实际生成结果 |
| 查询写入回执 | 幂等键与结果，不用盲目重复提交 |

统一提供可读输出和机器可读结果，区分冲突、无权限、会话失效、数据不完整、存储不可用。服务未运行时给出启动提示，不启用绕过业务规则的离线写数据库路径。客户端语言与 HTTP／JSON 方案见[技术选型](03-首版技术选型.md)，完整命令参数随实施计划的责任任务落实。

## 7. 导出、恢复与源码边界

### 7.1 两种不同用途的输出

| 输出 | 内容 | 用途 |
|---|---|---|
| 交接 Markdown | 某固定快照的可读摘要与引用 | 供后续会话理解上下文；不能完整恢复数据库 |
| 项目恢复包 | 一个项目的结构化记录、选定规格的冻结内容、受管理附件、完整性清单 | 在兼容版本中恢复工作台记录 |

恢复包不包含整个源代码仓库、未提交差异正文、依赖、运行环境、外部 URL 指向的内容、访问凭据或可继续使用的写会话授权。历史会话的标签、起止记录保留；敏感授权不保留。

用户主动上传的文件可能含项目内容，它们属于附件而非自动源码备份。导出前列明记录、附件、外链与未覆盖内容；用户另行负责源码备份和敏感内容检查。首版不自动向云端上传。

### 7.2 导出一致性

恢复包采用可解包的 ZIP 格式，包含版本化清单、结构化记录和按内容摘要组织的附件；清单列出 schema 版本、项目 ID、各文件长度及摘要。格式与限额见[技术选型](03-首版技术选型.md)，完整字段随实施计划的 T7、T8 落实，完整性和可验证性是必须满足的要求。

导出从一致的数据库读取快照选取全部项目记录，固定所需附件集合并防止被清理，校验附件后生成临时包，完整成功才发布输出文件。不直接复制正在写入的 SQLite 文件，不把半成品当作可恢复包。

写入预算与导出／恢复支持的规模使用同一计量规则；不得仅在导出时才发现合法累计写入超出格式限额。项目触顶后仍支持完整导出，导出所需操作状态不能反过来因项目配额阻塞导出。首版不分包或通过删除历史腾挪容量。该边界不免除磁盘满、附件损坏和版本不兼容等既有失败校验。

外部链接只携带引用；被用于有效决定的必要依据应显式纳入附件或保存足够的结构化记录。若受管理附件缺失或摘要不符，导出失败并列出具体引用，不能默默漏掉文件生成“成功”备份。

### 7.3 恢复流程

1. 在隔离暂存区读取清单，检查支持的格式版本、文件摘要、大小限制、记录 ID 与引用完整性；拒绝路径穿越、越界解包和异常规模归档。恢复不得执行包内脚本或命令。
2. 恢复到新的项目数据范围，不静默合并或覆盖同 ID 的现有项目。需要重试或恢复相同项目时使用独立数据目录；首版不提供冲突合并向导。
3. 附件完整就绪后，用数据库事务一次激活记录；失败保持已有项目不变，临时导入不出现在正常列表。
4. 保留历史 ID、基线、证据和决定；恢复的会话全部视为非活跃，旧写凭据失效，重新签发本机访问凭据。
5. 本机路径只作为参考，不自动相信包内绝对路径。用户重新绑定另行准备的源码工作目录并核对仓库、HEAD 和实际修改。
6. 绑定前可查看历史、规格快照与附件；涉及源码的新证据、工作区观察和续做写会话不可开始。历史已验收结论仍指向旧冻结版本，不因迁移自动改写。
7. 缺源码、缺原提交或缺依赖时明确提示其未恢复。不能通过“恢复成功”暗示能够马上复现测试或找回未提交修改。

完成提示分别报告记录／附件恢复结果和开发现场是否已具备。恢复包只恢复导出时的状态；导出后的新工作不在包中。

恢复激活前重新核算全部记录、唯一附件及恢复后的必要元数据。正常由本版导出的近上限包，须在兼容容量配置下验证恢复后仍可再次完整导出；不能相信包内自报用量，不能恢复成功后才发现新增元数据导致越界。恢复后接近预算仍提示，突破预算的后续新增写入按同一规则拒绝。

## 8. 首版验收场景

以下是未来实现必须验证的场景，不是本轮已经执行通过的测试。产品验证以真实项目为主，关键异常采用可控故障注入或针对性测试。

| 场景 | 预期结果 |
|---|---|
| 普通 Markdown 建立变更 | 无 Spec Kit 依赖；用户选定依据与条件后形成固定基线 |
| 原生规格继续编辑 | 旧基线不变，提示来源变化；采用新基线需用户确认 |
| 未提交且测试失败时保存 | 保存点成功保留进度与失败；不会被认定已验收或已备份源码 |
| 保存失败／磁盘满 | 不显示成功，最近成功保存点不前移，待提交内容可重试 |
| 累计容量接近或超过预算 | 提前提示；会超限的写入明确拒绝，最近保存点及已有历史不变，读取与完整导出可用 |
| 不同变更并发写入同一项目 | 累计预算事务校验，不因两个独立预检通过而合计越界；相同请求重试不重复计量 |
| 请求成功但响应丢失 | 按幂等键取回同一结果，不新增重复记录 |
| 工具 A 中断，工具 B 续做 | B 查询最新记录、核对实际文件、获得有效会话后继续 |
| 保存后还有未记录修改 | 展示实际差异，不按旧摘要覆盖或回滚文件 |
| 旧写会话延迟写回 | 接管后旧代次拒绝；Web 修改后旧记录版本拒绝 |
| 两个变更并行 | 不同工作区可写；同一工作区重复占用被拒绝 |
| 两个变更采用同条目的不同修订 | 基线独立、可分别验收，不自动同步或检测冲突；不宣称合并结果已验证 |
| 活跃会话下更换工作区绑定 | 拒绝；先结束或用户接管并关闭，再重绑、重新核对并开新会话 |
| 重绑定与开始会话并发 | 事务校验绑定版本与占用；不会把旧观察／延迟写回关联到新目录，历史路径不变 |
| 手改交接 Markdown | 工作台记录不变；重新生成不吞掉现有记录或冒充编辑已同步 |
| 交接生成失败 | 已保存进度保持成功，生成状态失败，可单独重试 |
| 证据只有计数或版本无法核对 | 可记录，不能批量通过或最终验收 |
| 未提交时测试，提交后上传 | 不把上传时 commit 冒充实际测试版本，要求重新验证或明确处理 |
| 基线或实现目标改变 | 旧证据与决定保留为历史；当前适用性需重新审阅 |
| 批量通过合格项 | 选中集合准确，每项独立决定，排除项及理由可见 |
| 批量预览后新失败或版本变化 | 整批拒绝并刷新预览，不部分默默成功 |
| 历史证据复用 | 用户确认适用理由后形成新决定，原验证版本不被改写 |
| 冻结 A、未采用的 B 出现失败 | 明确与 A 无关则提示但不阻塞；关联 A 或适用性未知则待处理，不能只凭版本不同排除 |
| 失败后补测成功 | 用户确认失败与补测的关联及理由后解除所指明阻塞；条件通过另有有效决定 |
| 集中确认失败处置 | 已解决／不适用逐条留记录；过期预览整批拒绝，豁免不能混入 |
| 显式豁免 | 单独确认缺口与理由，完成状态显示豁免数量 |
| 离线验收 | 冻结依据、版本和证据本地可核对时，远端不可用不阻塞 |
| 工作目录有尚未采用的新修改 | 明示验收只覆盖冻结 commit；文件变化不自动切换目标或否定旧证据；采用新目标后必须刷新预览 |
| 已验收后重新打开 | 新周期、新会话、重新确认依据；历史结论不被改写 |
| 导出与独立恢复 | 记录引用和受管理附件完整一致，外链范围清楚 |
| 近上限导出与恢复后再次导出 | 同一受支持配置下全部内容可往返，容量计量含必要元数据与封装开销，不靠截断通过 |
| 恢复包损坏／版本不支持 | 在激活前拒绝，不覆盖现有项目 |
| 恢复后旧凭据或源码缺失 | 旧写权限无效；可读历史，缺源码时不可开始续做 |
| 首次真实价值验证 | A 在小变更中保存未提交进度，B 核对后继续，用户验收，再完成独立导出恢复 |

## 9. 实施前保留的工程选择

本轮不再为已确认的产品边界增加问题。[技术选型](03-首版技术选型.md)已提出语言与框架、附件限额、安装启动、数据迁移和测试工具方案；[实施计划](superpowers/plans/2026-11-14-v0.1-minimum-loop.md)给出 CLI 能力、接口和任务顺序。依赖精确版本在 T1 验证并锁定，数据库字段和命令参数随责任任务落实；不扩大首版范围。

两种实际开发工具的接入效果、用户保存负担和数据规模需通过样本验证。若必要上下文必须靠反复人工补充，或用户仍需维护第二份进度文档，应先修正记录与交接流程，再考虑适配器和自动化。

首版不建设多人责任交接、专用 Git 记录分支、每次操作提交、强制远端刷新门禁、双向交接 Markdown 同步或 Spec Kit 自动导入。历史 ADR 记录取舍，当前主方案与本文共同定义实施范围。
