## 1. 推荐结论与取舍

推荐 **TypeScript＋Node.js 本地服务＋Fastify＋React／Vite＋SQLite**。Web 和薄 CLI 共享协议定义，由同一个服务执行业务规则；生产运行只启动一个本地服务进程，提供 API 和构建后的静态页面。

主要理由是本产品的难点在版本、会话和记录一致性，不在模型推理或高吞吐计算。使用一种语言可以减少 Web、CLI、服务端之间的契约重复，也便于个人持续维护。代价是需要掌握 TypeScript 与前端工具链，并验证 SQLite 原生模块的 Windows 分发。

| 候选 | 优势 | 当前代价与结论 |
|---|---|---|
| 全栈 TypeScript | 一套契约、同一运行时，Web 与 CLI 便于一起分发 | 原生 SQLite 安装须验证；作为首选 |
| Python＋FastAPI＋React | Python 对后续脚本和 AI 处理方便 | 当前没有模型执行需求，却需维护两套类型和运行环境；作为未来重评备选 |
| Java＋Spring Boot＋React | 用户熟悉后端体系，可可靠表达事务 | 仍需前端工具链与额外运行环境；对当前本机小产品收益不足，不因熟悉就默认采用 |

不同时维护多个后端，不引入 Electron／Tauri、Next.js 全栈服务器、Redis、ORM、任务队列或插件框架。未来若需要模型调用，可在明确需求出现后接入，不为假设中的 AI 子系统增加 Python 服务。

## 2. 技术栈与版本策略

| 层次 | 推荐选择 | 用法与约束 |
|---|---|---|
| 运行时 | Node.js 24 LTS 的实施时最新安全补丁 | 首版只承诺验收过的 24.x；不跟随 Current 或预发布版本 |
| 语言与包管理 | TypeScript、npm、ES Modules | 单仓库单 package.json；strict 类型检查；package-lock.json 固定依赖 |
| HTTP 服务 | Fastify 5 | 本机 JSON API、来源与凭据校验、统一错误；不拆微服务 |
| 数据契约 | TypeBox＋官方 Fastify Type Provider | JSON Schema 与 TypeScript 类型同源；服务端仍执行运行时校验 |
| 页面 | React 19＋Vite，React Router 声明式路由 | 纯客户端页面；构建产物由本地服务提供，无 SSR |
| UI 状态与样式 | React 局部状态、统一 API client、原生 CSS | 不引入 Redux、组件平台或主题系统；写成功后刷新服务端状态，不乐观显示验收成功 |
| 记录存储 | better-sqlite3＋参数化 SQL | 同步短事务；编号 SQL 迁移；不引入 ORM 或事件溯源框架 |
| 附件与摘要 | Node.js 文件流、crypto SHA-256 | 不可变内容寻址文件，显式引用，不把源码自动复制为附件 |
| 工作区观察 | 已安装的 Git CLI＋Node.js 文件读取 | 参数数组启动子进程，禁止经 shell 拼命令；工作台仅执行只读 Git 操作 |
| 薄 CLI | Node.js 内置参数解析与 fetch | 共享协议，只访问服务；复杂正文经 UTF-8 文件或 stdin 输入，避免 PowerShell 引号问题 |
| 恢复包 | ZIP，yazl 写入、yauzl 逐项读取 | 项目侧额外验证路径、大小、引用和摘要；不依赖解压库替代业务完整性检查 |
| 自动验证 | Vitest＋Fastify inject＋Playwright | 规则单测、真实临时 SQLite／Git 集成测试、少量真实浏览器闭环 |
| 日志 | Fastify 日志能力＋统一 requestId | 记录错误与操作标识；默认不输出凭据、正文、附件内容 |

版本核查截至 2026-11-14：Node 官方仍列 24 为 LTS；Vite 文档给出的 Node 门槛可被 24.x 满足。这里选择 24 是兼容基线，不声称它是最新主版本。[Node 发布状态](https://nodejs.org/en/about/previous-releases)、[Vite 环境要求](https://vite.dev/guide/)。

Fastify 按受支持 Node LTS 线的最新补丁提供支持；TypeBox Provider 有明确的 Fastify 版本兼容表。实施 T1 必须核对 Fastify、Provider、TypeBox 的 peer dependencies，不能混用旧版 @sinclair/typebox 示例和新版 typebox 包。[Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)、[Provider 兼容表](https://github.com/fastify/fastify-type-provider-typebox)。

React 采用 19 系列；React Router 仅采用声明式模式。Vite、Vitest、TypeScript、Router 和辅助依赖的精确稳定版本在 T1 安装验证后写入锁文件与环境记录，不用本文猜测补丁号，也不让后续任务使用浮动 latest。[React 版本](https://react.dev/versions)、[Router 模式](https://reactrouter.com/start/modes)、[Vitest 要求](https://vitest.dev/guide/)、[TypeScript 项目安装](https://www.typescriptlang.org/download/)。

## 3. 运行、分发与数据位置

首版面向 Windows x64 开发机，优先在 Windows 11 与 Chromium 浏览器验证。Playwright 当前官方支持 Windows 11+；Windows 10、ARM 和其他 OS 暂不作已验证承诺。[Playwright 系统要求](https://playwright.dev/docs/intro)。

开发时允许 Vite 和 API 两个进程，浏览器经开发代理访问 API；生产使用一个 Fastify 进程提供静态页面与 /api/v1。开发凭据与允许来源必须显式配置，不能把宽松开发规则带入生产。

首版分发为一个带编译后服务、CLI、静态页面和迁移文件的 npm 安装包；先以本地 tgz 验证，无须发布 npm 或 GitHub。用户需预装 Node.js 和 Git；不承诺无需运行时的 exe，不自动安装系统依赖。运行入口计划为 specmill serve，开发和本地安装方式在 README 中说明。

数据默认放在本机用户应用数据目录的 SpecMill 子目录，提供 --data-dir 覆盖。数据目录内分别保存数据库、attachments、exports、staging 和凭据；不得默认放入源码仓库、网盘同步目录或网络文件系统。一个数据目录只允许一个服务实例，启动冲突给出提示，不自动抢占。

运行端口默认 43127，允许 --port 指定；被占用时失败并告知处理方式，不静默另起实例。只绑定 127.0.0.1；检查 Host／Origin，Web 写请求带 CSRF 防护，CLI 使用独立 Bearer 凭据。用户登录凭据由本机启动流程发放，浏览器使用 HttpOnly、SameSite=Strict 会话 cookie，凭据不进入 URL、页面正文、日志或恢复包。首版仍不把同 OS 用户下的恶意工具当作可隔离对象。

## 4. 存储与一致性实现约束

- 数据库使用 WAL、foreign_keys=ON、synchronous=FULL、busy_timeout=5000ms；这些是工程默认值，不是已测性能结论。
- 运行时读取 SQLite 实际版本，要求至少 3.51.3。官方已记录旧版本的 WAL-reset 问题及修复版本；不能只看 npm 驱动版本就假定底层 SQLite 合格。[SQLite WAL 修复说明](https://sqlite.org/wal.html)。
- 服务内一个写连接；写事务只做权限、版本与会话校验，以及记录／历史／回执更新。文件 I/O、Git 观察和 ZIP 操作在事务外完成，不在同步事务回调中 await。[better-sqlite3 事务限制](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)。
- 会话唯一性同时由数据库约束与应用校验保证；校验和写入处于同一事务。存储仍以普通表、外键和不可变历史记录表达，不建设通用事件总线。
- 每次修改返回记录版本与幂等回执。请求失败、结果未知、业务拒绝分开表示；客户端不能因为超时就产生新 requestId 重做一次。
- 附件先落受控临时文件并校验，再原子放入内容寻址目录，最后写引用。文件成功、数据库失败允许留下无引用文件；首版仅清理确认无引用的 staging，暂不提供历史附件自动清理。
- schema 版本高于程序支持时拒绝写入；迁移之前用驱动备份接口产生数据库备份，保留不可变附件，迁移失败不继续提供写服务。恢复包格式与数据库 schema 分开编号，首次均为 1。
- 导出使用一个短的数据库读取事务，将限定规模的项目结构化记录序列化为固定内存快照，再流式复制并校验不可变附件；后续记录写入不会进入该包。无附件自动清理，避免导出期间引用被回收。绝不直接复制运行中的 db 文件当恢复包。

better-sqlite3 官方提供主要平台／架构的预编译二进制，但具体 Node 24＋Windows x64 组合仍须 T1 实测。若安装需要额外 C++ 编译环境，暂停扩展功能，先核对依赖版本与分发方案；不能未经说明给用户机器安装编译工具链。[驱动安装说明](https://github.com/WiseLibs/better-sqlite3)。

## 5. 首版限额与错误语义

以下限额用于控制初版内存和失败恢复范围，是可调整的工程起点；达到边界必须提示，不丢弃或截断数据冒充完整保存。

| 对象 | 初始限制 |
|---|---|
| JSON 写请求／单份保存点 | 1 MiB UTF-8 |
| 单份规格文件／待计算摘要的单个未跟踪文件 | 2 MiB／20 MiB；超限显示未覆盖 |
| 工作区观察 | 最多 10,000 个变更项；Git 子进程 15 秒超时，超限标记不完整 |
| 单个附件 | 20 MiB；首版只接受纯文本、JSON、PNG、JPEG、PDF，默认以下载方式提供 |
| 单项目恢复记录 | 序列化 JSON 不超过 20 MiB |
| 恢复包 | 压缩体与累计解压内容分别不超过 1 GiB；最多 10,000 个文件项 |
| 普通 HTTP 请求 | 客户端等待 30 秒；超时后用原 requestId 查回执 |
| 导出／恢复 | 本机每次一个操作，最长 300 秒；浏览器轮询状态，可取消准备阶段，激活事务不可中途取消 |

ZIP 只允许 manifest.json、records.json 和 attachments 下的摘要命名文件；拒绝重复项、大小写碰撞、绝对路径、..、符号链接、Windows 盘符／设备名／数据流路径。逐项读取并统计实际解压量，不能信任声明的长度。[yauzl 读取与大小校验](https://github.com/thejoshwolfe/yauzl)、[yazl 输出](https://github.com/thejoshwolfe/yazl)。

错误以固定 code、中文说明、requestId 和必要的当前版本返回。HTTP 分类：400 无效输入，401／403 凭据或能力不足，409 版本／会话／状态冲突，413 超限，422 证据或恢复内容不满足业务约束，503 存储／本机服务暂不可用。数据库损坏进入不可写状态，不当作普通可重试冲突。

CLI 成功返回 0；参数错误 2；冲突 3；权限错误 4；证据／恢复校验失败 5；服务或 I/O 故障 6。--json 时 stdout 只包含机器结果，提示与诊断进 stderr。实际退出码及 HTTP 映射必须用契约测试锁定。

## 6. 验证与开放边界

关键业务规则先写失败测试再实现，数据库、文件、Git 和进程边界用真实临时环境测试，不用全 mock 宣称可靠。Fastify inject 用于路由与权限测试，Playwright 只覆盖真实页面关键路径；不是每个组件都写镜像实现的测试。[Fastify 测试方式](https://fastify.dev/docs/latest/Guides/Testing/)。

所有测试数据写入显式临时目录，测试仓库与真实开发仓库隔离；进程终止测试只能终止测试自身启动的进程。人工验证必须记录工具组合、实际版本、成功步骤和未覆盖内容。

当前只检查到本机已有 Node 24.12.0、npm 11.6.2、Git 2.45.1；它们不是最终锁定版本，也不证明新依赖已兼容。T1 应使用受支持的最新 24.x 补丁建立基线；系统运行时升级另行说明，不在本轮执行。

开源许可证、GitHub 仓库创建和公开发布不阻塞本地闭环。本轮不创建 LICENSE、不初始化仓库、不提交、不推送、不安装软件。精确的实施顺序、文件责任和每步验收见配套计划。
