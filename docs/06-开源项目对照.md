# 团队怎样围绕一份规格交付变更

2026-11-21 核对三个官方仓库的文档与模板，链接均固定到当日可读的提交。团队首试优先验证内置工作流执行与 Agent 调度。建议以 LoopForge 的执行、退回与人工放行为主线，用 Spec Kit 的场景模板描述完成条件，用 OpenSpec 的增量规格组织审阅。实际使用效果仍需通过试点观察。

## 三个项目各解决什么问题

| 项目 | 原作中的具体做法 | 对 SpecMill 的建议及取舍 |
|---|---|---|
| **GitHub Spec Kit** | 仓库提供一条完整工作流，依次生成规格、计划、任务，再实施；规格和计划各有审阅步骤。规格模板给每个用户故事标优先级、独立测试方法和 Given/When/Then 场景，任务模板按故事分组。[工作流](https://github.com/github/spec-kit/blob/a4d571229e164e440f8950cac034607bae7b7518/workflows/speckit/workflow.yml#L44-L79) · [规格模板](https://github.com/github/spec-kit/blob/a4d571229e164e440f8950cac034607bae7b7518/templates/spec-template.md#L26-L37) · [任务模板](https://github.com/github/spec-kit/blob/a4d571229e164e440f8950cac034607bae7b7518/templates/tasks-template.md#L10-L22) | 在规格审阅时问“谁在什么条件下做什么，怎样看出成功”。对每个可独立交付的行为给出验收示例。小变更可在一份 Markdown 中表达，采用示例并不需要引入全套命令或自动导入。 |
| **Fission AI OpenSpec** | 团队指南推荐将一个变更放入一个分支和 PR。审阅者先读提案，再读增量规格，最后核对实现。默认 schema 将新增、修改、删除和改名分开表达。团队可在合并后归档，也可将归档纳入同一 PR；归档会将增量并入共享规格。[团队工作流](https://github.com/Fission-AI/OpenSpec/blob/0c737dc1b543249b38b0f4716816fcf493d894dd/docs/team-workflow.md#L17-L56) · [增量规格](https://github.com/Fission-AI/OpenSpec/blob/0c737dc1b543249b38b0f4716816fcf493d894dd/schemas/spec-driven/schema.yaml#L95-L108) | 让评审人一眼看到“原行为、本次修改、受影响的验收场景”。PR 可以链接对应变更。共享规格归档解决团队持续维护的问题，SpecMill 单次验收仍应指向当时采用的基线和实现版本。 |
| **腾讯 LoopForge** | 平台展示的 SOP 包含需求澄清、设计、实现、独立评审、脚本测试和人工验收。每个节点声明产物与依赖。人工关口可以放行、补充信息后重跑当前节点，也可以退回上游返工。[官方流程与节点定义](https://github.com/Tencent/LoopForge/blob/afc6e7d189d11bdcd7430d3b17a6f022d33550fd/README.zh-CN.md#L140-L168) | 首试内置一条固定工作流，由调度器实际启动实现和评审 Agent，保存每次执行的输入版本、输出、失败位置及返工目标。关键决定留给负责人。画布设计器与任意 SOP 编排可等固定流程得到验证后再评估。 |

### LoopForge 的两个实现细节

LoopForge 判断一个节点能否执行时，只考虑仍在等待的节点，并逐一检查其前驱是否成功。定位某次运行对应的流程时，优先使用运行中保存的流程快照，缺少快照的旧记录才回查流程定义。两个规则分别回答了“现在可以执行什么”和“重试时按哪版流程执行”。[节点就绪判定](https://github.com/Tencent/LoopForge/blob/afc6e7d189d11bdcd7430d3b17a6f022d33550fd/internal/engine/workflow_graph.go#L11-L32) · [运行快照的选择](https://github.com/Tencent/LoopForge/blob/afc6e7d189d11bdcd7430d3b17a6f022d33550fd/internal/engine/workflow_graph.go#L41-L51)

建议 SpecMill 给每次运行固定流程修订和任务图修订，给每条证据另外绑定规格基线与实际提交。前者保证返工能找到正确的执行步骤，后者让验收人能判断旧结果还能否用于新提交。例如测试脚本在 H1 成功，随后集成提交变为 H2，调度历史仍可重放，但 H2 的验收需要重新核对证据。

## 一次团队试点怎样走

下面以“使下载报告的文件名带日期”为例。表中的执行器、调度和角色分工是团队版的试点设计。历史 v0.1 设计覆盖个人本机续做与冻结验收，供对照原有边界。[历史首版设计与不变量](02-首版详细设计.md#1-系统边界与不变量)

| 环节 | 谁来做 | 下一位应拿到什么 |
|---|---|---|
| 1. 描述行为变化 | 需求负责人 | 写明现状 `report.csv`，预期按项目时区取导出日期。给出两个可观察的场景：跨日边界时文件名日期正确；下载内容保持一致。 |
| 2. 审阅规格 | 同伴审阅，负责人确认 | 先看场景。若“日期”可能指数据所属日或导出日，先请负责人选定，再固定本次采用的规格版本。实现者能据此写出测试。 |
| 3. 实现和测试 | 调度器、实现 Agent、测试脚本 | 负责人放行后，调度器将已确认规格和目标工作区交给实现 Agent。脚本针对产出的实现版本运行两个场景，写回运行结果与日志。中断时保留尝试记录和实际文件位置。 |
| 4. 审阅与返工 | 调度器、独立评审 Agent、负责人 | 调度器把增量规格、实现版本、差异和测试证据交给评审 Agent。若只有平日样例，负责人可按评审意见退回实现节点。调度器开新尝试并关联原失败，为更新后的实现重新执行受影响的检查。 |
| 5. 验收与归档 | 验收负责人、仓库维护者 | 负责人记录本次确认的条件、规格和实现版本。维护者按团队约定合并、更新长期维护的规格并链接 PR。验收决定、代码合并和规格归档各有可追溯的记录。 |

首轮试点应实际触发一次失败返工和一次人工放行。观察调度器能否从指定节点继续，负责人能否从验收条件追到相关尝试、实现提交、测试结果和最终决定。
