# 切片 C 验证与性能

## 执行器契约

团队运行的 `dates` 和 `paid` 共用执行器协议 v1。Worker 将固定任务提示经 stdin 交给选定 CLI。守护进程限制调用时间为 90 秒，限制事件流和最终输出大小，只保留最终文本与白名单内的执行器、模型、耗时和用量字段。Worker 解析 SQL 谓词并生成提交。集成尝试和服务端独立复核均从冻结规格与两项工件重建 Git 证据，再测试目标提交。

| 执行器 | 已验证版本 | 启动边界 |
| --- | --- | --- |
| Codex CLI | 0.169.0 | 原生可执行文件、临时只读会话，关闭 shell、外部工具和用户配置 |
| Pi Coding Agent | 1.5.2，`deepseek/deepseek-flash` | 用当前 Node 启动受信 JS 入口，关闭工具、MCP、扩展、skills、上下文文件、更新检查及会话持久化，校验实际模型标识。每次调用使用不含 Pi 项目配置的合成工作区 |

服务启动时选择一种执行器。沿用项目并发上限、当前授权和尝试代次校验。Pi 由本机默认认证目录或传入的 `DEEPSEEK_API_KEY` 鉴权。两种 CLI 作为本机受信程序运行，模型调用限于合成数据。Windows 在 CLI 进程存活时通过其 PID 终止进程树。

`tests/integration/team-executor-contract.test.ts` 对二者运行同一套检查，包括失效入口、启动前取消、冻结派工、任务提交内容、两父提交、独立集成复测、具名验收与归档。另用可控 Pi 进程验证运行中取消，检查该进程 PID 已消失。真实调用需配置以下环境变量。常规测试在执行器入口缺省时跳过对应的真实调用。

## 压测环境与口径

2026-11-21，Windows x64、i5-13600K、20 逻辑处理器、63.75 GiB 物理内存、NVMe SSD、Node 24.22.3、SQLite 3.53.2、Git 2.45.1.windows.1。账本进程绑定 4 个逻辑处理器。Git 工作流突发试验使用全机 CPU，持续试验通过 Windows Job Object 将进程树限制到 4 个逻辑处理器与 8 GiB 已提交内存。操作系统缓存未清理，跑次有重叠并共享主机和磁盘。[Windows Job Object 资源限制](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)

- **账本负载。** 单服务进程、单 SQLite WAL 连接，`synchronous=FULL`。10 项目，预热后起步 10,000 条历史运行，始终补齐 80 个未完成运行。每轮 100 项操作，由 70 次含成员鉴权的状态查询、10 次领取、10 次确认租约仍有效、10 次结果提交组成，补充运行额外计量。切片 C 沿用固定租约，使用有效性检查模拟租约流量。操作在服务端串行执行，延迟含 SQL 和事务，客户端传输与事件循环等待另见 HTTP 负载。Git 和模型均用确定性工件替代。
- **带 Git 的 HTTP 负载。** 10 项目分别提交 3 条运行，100 个错峰轮询客户端走回环 HTTP，每个客户端每 200 ms 再发请求且最多有 1 个在途请求。Worker 用固定 SQL，走真实 fork、独立 Git 提交、服务端重建和测试，以及具名审批和归档。每次使用新数据库，采样区间从首个运行提交至最后一个归档完成。p99 样本量有限，30 个样本的 p99 即最大值。
- **HTTP 持续试验。** 沿用同一脚本和 100 个轮询客户端。15 分钟内每完成一个归档，就向同一项目补充一条运行，到点后处理剩余队列。
- **排队。** 从运行提交到首个任务领取。账本的 80 指待完成运行上限，包含已领取的运行。HTTP 工况一次投入 30 个运行。两个工况都另外报告实际吞吐，耗时以最近秩法取百分位。
- **数据库。** `SQLITE_BUSY` 计数用于观察锁冲突。正常负载使用单写入连接，无竞争写入者，计时无法从同步 I/O 中独立归因锁等待。事件循环延迟用于观察同一服务线程被数据库和任务编排占用后的影响。两套假执行器工况的模型成本均为 0。

```text
node scripts/bench-team.mjs 900 10 10000
node scripts/bench-team.mjs 25 25 2000
node scripts/bench-team.mjs 25 50 2000
node scripts/bench-team-workflow.mjs 2 3
node scripts/bench-team-workflow.mjs 6 3
node scripts/bench-team-workflow.mjs 8 3
node scripts/bench-team-workflow.mjs 6 3 43139 900
```

`bench-team.mjs` 的第四个位置参数可指向从旧实现构建的服务目录。对比基线为切片 B 的 `df71db6`。两个脚本均写入临时数据目录，并输出 JSON 指标。

## 性能结果

### 账本 15 分钟长测

每轮预置 10,000 条历史运行，投放目标 1,000 ops/s。

| 实现 | 实际 ops/s | 到待审阅/秒 | 查询 p95 / p99 | 领取 p95 / p99 | 写回 p95 / p99 | 首次排队最长 | 事件循环 p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 切片 B 基线 | 13.5 | 0.44 | 0.81 / 1.71 ms | 1,314.51 / 2,146.07 ms | 5.49 / 11.06 ms | 230.08 s | 16,886.3 ms |
| 第一轮部分索引 | 193.6 | 6.45 | 0.79 / 1.96 ms | 79.50 / 155.34 ms | 6.80 / 14.26 ms | 32.84 s | 1,674.6 ms |
| 最终实现 | 693.0 | 23.10 | 0.50 / 1.43 ms | 18.33 / 34.64 ms | 7.22 / 18.86 ms | 5.77 s | 291.8 ms |

第一轮长测有 83% 的采样窗口落在同步领取调用。逐语句计时和完整查询计划发现，租约扫描的 `ORDER BY a.rowid` 让 SQLite 仍沿表顺序读取所有历史尝试。最终实现明确从 `team_running_attempts` 取得活跃集合再排序，保留过期租约的处理次序。

最终长测完成 623,700 项操作，10 个项目各有 2,079 个运行进入待审阅。首次排队 p95 / p99 为 4.30 / 5.24 秒。所有账本跑次的非预期错误和 `SQLITE_BUSY` 均为 0。最终吞吐为目标的 69.3%，领取仍占本轮约 44% 的采样时长，写回与补充运行合计约占 37%。

`EXPLAIN QUERY PLAN` 显示，原先领取任务扫描历史任务表，项目并行数检查遍历该项目的历史运行，过期检查扫描尝试表。新增部分索引并固定过期扫描的索引后，领取与恢复围绕活跃记录执行。公平派工、授权约束与事务持久化均保持原语义。短轮高于约 0.9–1.0k ops/s 的投放明显出现积压。最终的 5,000 ops/s 短轮与 HTTP 持续试验启动并行，结果显示共享资源下的波动，饱和点需要在目标环境单独定标。

**独立锁竞争探针。** 在临时 WAL 库中用第二个连接注入 0 / 50 / 150 ms 写锁，空 `BEGIN IMMEDIATE` 事务往返分别为 1.69 / 71.45 / 167.15 ms。探针刻意引入竞争，正常负载仍采用单写入连接。

## 第二轮性能复测

本轮以 `a15cf09` 为代码基线，沿用同一台 Windows 主机、Node 24.22.3、SQLite 3.53.2 和 Git 2.45.1。账本沿用单写入连接和 `WAL + synchronous=FULL`，事务仍同时提交状态、事件和回执。派工一次汇总活跃任务数，继续按项目轮转、运行入队顺序和任务顺序领取。连接复用固定 SQL 模板的预编译语句。

Worker 批量写入两条任务提交和集成提交，校验工件 SHA 后更新工作区索引及 HEAD。服务端在另一个临时仓库中重建冻结基线、两条任务提交和集成提交，再批量回读目标对象，核对父提交及文件字节并重新执行三项 SQLite 验收。一次验收复用独立的内存数据库，逐例替换整张测试表并以只读模式执行。固定历史样本验证了基线、任务和集成提交的 SHA 兼容。[Git 批量导入](https://git-scm.com/docs/git-fast-import) · [Git 批量对象读取](https://git-scm.com/docs/git-cat-file)

### 诊断和复测口径

新脚本额外记录完整分钟的实际操作数。除上方历史长测外，本轮还留存原版与候选版各 75 秒复测，参数均为 10 项目、预置 10,000 条历史运行及 1,000 ops/s 投放。短轮受同时段主机负载影响，两版实际为 999.78 与 903.93 ops/s。用相同数据形状进行的 50,000 次内存诊断，领取累计耗时从 2,504 降至 953 ms，读取从 4,057 降至 1,882 ms，写回从 1,332 降至 611 ms。内存诊断用于观察 SQL 与应用开销，磁盘性能以 WAL 长测为准。

Git 分段复测以原版生成的任务工件为输入，交替运行原版与优化版。每次在新仓库测 Worker 集成和服务端独立复核，并断言两版的提交、父提交、SQL 和测试结果一致。HTTP 长测继续用 4 个逻辑处理器、8 GiB 进程树上限、10 项目、100 个客户端、6 个 Worker 和 900 秒投放。可为 HTTP 脚本指定第五个参数，收齐所有合成归档后统一保存 JSON。每份归档核验项目、冻结摘要、实施成员、独立审阅成员及验收提交。
