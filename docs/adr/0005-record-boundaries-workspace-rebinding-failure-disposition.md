# 记录权威边界、工作区重绑定与失败处置

用户在 grill-with-docs 中确认 Q14—Q16，要求同步设计文档，暂不编写代码、不提交或推送。

1. **Q14：各记录源分工明确。** GitHub Issues 管 SpecMill 自身的待办、问题和公开讨论；仓库 Markdown 管项目设计；工作台管具体变更的冻结依据、续做记录与验收决定。首版只保留必要链接，不同步状态；关闭 Issue 不等于工作台验收通过。这样避免三处重复维护同一状态，也不把仓库协作配置变成产品必须集成 GitHub 的要求。
2. **Q15：活跃会话期间禁止更换工作区绑定。** 先正常结束会话，或由用户接管并关闭会话，再明确绑定新目录、核对仓库及实际文件并开启新会话；接管本身不等于已经关闭。历史保存点保留当时的路径和观察，不随当前绑定改写。以显式切换替代透明改指向，避免延迟写回关联错误目录。
3. **Q16：失败按当前验收上下文判断适用性，解除须显式记录。** 明确属于其他版本且与当前上下文无关的失败保留并提示，不自动阻塞当前冻结目标；相关或适用性未知的失败必须处理。用户确认补测证据解决了哪些失败，或认定不适用，分别记录关联及理由；接受风险仍走独立豁免。可集中审阅确认解决／不适用，但不能由后到成功记录自动覆盖失败，也不能隐式豁免。

失败处置补充验收依据，不改写原始证据，也不自动形成条件通过决定。上述决定分别落实到协作约定、详细设计和 T2／T3／T5／T6／T8 的契约与验收场景。
