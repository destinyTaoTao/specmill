# #19 容量实测：20 MiB 边界的写入、导出与恢复

2026-11-28，使用 SpecMill 安装包的默认配置，六个独立合成项目均完成了导出、恢复和再次导出。其中三个项目距上限 4,217 B，另三个项目恰好用完 20,971,520 B。六对 ZIP 中的 `records.json` 和所有附件逐字节一致。记录占比最高的满额项目恢复花了 242.58 ms，服务进程峰值工作集为 221.3 MiB，是本次六次恢复的最高值。

## 测量与核对方法

- 环境为 Windows 11 build 26200、Core i5-13600K、Node 24.22.3。使用前一轮从 `db6cd01` 生成的安装包重新离线安装，包 SHA-256 为 `078295a7df6a2dd0ed557395c89d4183d230bc63e3fffa6a696ca890af918d31`。后续的 `867c05e` 仅更新文档。
- 用打包服务的本机 HTTP 接口新建项目，用草案修订和唯一二进制附件逐步填充。每次修订更新目标、范围、排除项和 8 项条件，历史及请求回执一起计入记录预算。附件使用固定种子的不同内容。测试未调低限额，直接使用 20 MiB 默认配置。
- 客户端按单调时钟测量。导出从提交导出请求计至 ZIP 下载完成；恢复从发送 ZIP 计至收到已激活回执。每个阶段在独立启动并已登录的服务进程中串行执行。进程启动、数据目录锁等待和客户端事后校验不计入表内；磁盘缓存未清空。
- 内存取自 Windows `GetProcessMemoryInfo` 的 `PeakWorkingSetSize`。表内三阶段的进程从启动到登录后的当前工作集为 82.3–83.6 MiB，报告的峰值包含这部分。累计写入单独计量。客户端、浏览器、文件缓存和其他系统进程不计入服务进程工作集。
- 两次导出均核对服务报告的 ZIP 长度、SHA-256、包内清单及每个条目的长度与摘要。按初始写入数据核对修订数量、附件内容及其引用。最后独立解开两次导出的 ZIP，比较完整记录和所有附件，再与两端磁盘文件对照。清单含各自生成时间。

本次覆盖当前版本、Windows 本机、单项目串行操作，以及三种草案历史和附件占比。每种组合实测一次，表中数值用于描述本机观测。旧版包、并发负载和更多小文件使用各自的验证记录。本轮没有操作[第一组双工具交接样本](2026-11-28-k19-real-handoff.md)，该组的目标确认、失败处置和最终验收仍由用户在 Web 决定。
