# #19 实测：Codex 交给 Pi，恢复后继续审阅

2026-11-28，在 Windows 本机用同一个合成变更做了两轮对照。Codex 桌面会话负责交出工作，Pi 1.5.2（DeepSeek，`deepseek-flash`）在独立新会话接手。两条路径都修对了问题，均未向发起方补问业务上下文。普通 Markdown 在两轮中都更快。SpecMill 多留下了可以在恢复后核对的记录，包括原失败、对应冻结条件、目标提交候选和复测证据。用户选择亲自在 Web 验收，两项条件均保留待定。

## 对照方法

- 样本要求清理标签首尾空白并转成大写，同时去重并按 ASCII 排序。Codex 留下部分实现和未提交修改。交接时两个测试一过一败，排序仍失败。两条路径使用相同规格、冻结口径、测试与待续做摘要，分别在独立的 Git 目录执行。
- 普通 Markdown 包含目标、已做、失败、未验证、阻塞、下一步以及 Git 状态。SpecMill 路径使用由提交 `db6cd01` 打包并离线安装的 CLI，记录失败执行和对应证据，保存检查点，生成快照，再释放写会话。两条路径都从已经写好的摘要开始计时，排除构思和撰写这段共同文字的时间。
- 每次接手都启动新的 Pi 进程。给它交接文件位置、规格和测试的入口，以及本轮检查和交付命令的用法。Pi 可自行读、改、执行命令，无法读取前一工具的对话。两侧用脚本执行 Git 与测试步骤，SpecMill 侧由脚本额外调用真实 CLI 登记会话、记录、附件、证据和候选。此处衡量的是这套可重复操作的工作流。

## 对项目价值的判断

这个短任务中，写齐内容的 Markdown 足以让另一工具继续工作。固定 LF 的一轮里，SpecMill 多花约 8.6 秒交出工作，接手至交付多花约 13.7 秒。此次观察到的收益集中在审阅与恢复：换了源码目录，用户仍能查清哪项失败、哪个提交重测过、证据在哪里、哪些决定还要亲自作出。一个合成任务和两轮在线模型调用，只能说明这个样本的结果。

建议先试一次 CLI 调用完成保存点、快照和释放会话，保留各步回执与失败后的重试能力，再用相同样本复测「交出工作」的 8.703 秒。此轮只测了整段耗时，各次 CLI 启动和服务写入分别占多少仍待测量。
